## 2. 🟡 协商区 —— 我必须改，但对每个改动负责

**规则**：最小 hunk；改完在 §5 登记；发现别人正在改同一文件就先沟通再 rebase。

| 路径 | 为什么必须改 | 预期改动量 |
|---|---|---|
| `tools/package-client.mjs` | `SHELL_FILES`（**`tools/package-client.mjs:218`**，实测行号）把 `shell/<name>` 映射到 payload 的 `js/shell/<name>`，消费点在 `:160`。**不加这里，我的新壳文件根本不会进 payload。** | 追加 N 行到数组 |
| `shell/picker.js` | 挂载入口：1 处 `import`（约 25 行区域）+ 1 处调用 | ≤ 3 hunk |
| `shell/picker-core.js` | **尽量不改**。纯函数一律放我自己的 `shell/p2p/rooms.js`；只有确实属于「选服规则」且要在 UI 层复用时才动 | 0，或极少 |
| `agents/README.md` | 只在登记表**追加一行** | 1 行 |
| `test/packaging.test.js` | **只有**当我的改动影响了「3 文件 7 hunk」这类被钉死的计数时才动 | 条件性 |
| `docs/PACKAGING.md` | 同上 | 条件性 |

⚠️ **实测超预算**（2026-10-11）：`shell/picker.js` 的 M1 UI 接入是 **6 hunk / +81 行**，不是上表写的「≤ 3 hunk」。
逐 hunk 拆分见 §5 —— 1 处状态块 + 1 处两个函数 + **4 处调用点**（`renderList` / `loadList` / `layout` / `destroy`），
4 个调用点在文件里分散，diff 上下文不重叠，无法并成更少的 hunk。**是否接受由 owner 定**；若要压回 3 hunk，
唯一办法是把 lobby 生命周期挪进 `shell/p2p/` 的新模块、由 picker 只做注入（代价：`SHELL_FILES` 再多一行）。

⚠️ 后两项是连体婴：`AGENTS.md` §4 明确要求 `test/packaging.test.js` 的文件数/hunk 数与
`docs/PACKAGING.md` 的「N 个文件、N 个 hunk」**三处同步**，否则数字互相说谎。
我 M1/M2 阶段不动 `patches/`，所以理论上不该触发 —— 一旦触发，说明我越界了，先停下来。

## 6. 冲突处理规程

1. 改黄色区文件前，先看最近谁动过它：
   `git log -3 --format='%h %an %ad %s' --date=short -- <file>`
2. 若 `git fetch` 后发现同一文件在别人的分支上也有改动 → **先在此目录留言**（`agents/p2p-match/NOTES.md`），
   再决定谁先合并。
3. **后合并者负责 rebase**，不把自己的冲突丢给对方。
4. 一律走 `feat/p2p-match` 分支 + PR，**不直接推 `main`**。
